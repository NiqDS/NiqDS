# Исходное ТЗ (оригинал, без изменений)

> Извлечено из приложенного `.docx`. Приведено дословно для трассируемости
> решений в `README.md` -> "Assumptions & open questions".

## Платформа автоматизированного АБ тестирования

### Обзорно:

В рамках пайплайна требуется реализовать функционал, при котором при подаче
агенту списка ИНН ЦГ и после оценки всех требуемых показателей, а также
предоставленных параметров измерения фин. эффекта, агент самостоятельно
собирает файл с группой КГ и ЦГ ИННок для пользователя + (копия этих списков
& параметры пилота (название, срок, измеряемые показатели фин. Эффекта,
ожидаемый эффект (в %)) передается команде аналитиков и локально создается
папка с названием и сроком пилота для мониторинга. После получения групп КГ
и ЦГ, срока пилота и измеряемых показателей, агент выбирает скрипт, по
которому рассчитываются фин. эффекты и результат сохраняется в Excel
документ для сохранения в папке пилота. При пересчете и добавлении записей
в документ по мере проведения пилота, документ перезаписывается с новыми
месяцами / датами. После расчета, Excel файл с расчетами загружается в
Навигатор для построения дешборда, где наглядно показана успешность пилота
в течении его проведения.

### Пререквизиты:

1. Пустая таблица, в которую будут заполняться ИННки, участвующие в пилотах.
   Схема = (no, inn, valid_from, valid_to, email_submitter, report_date), где:
   no – номер строки (техническое поле), valid_from/valid_to – срок действия
   пилота, email_submitter – почта того, кто прислал ИННки, report_date –
   дата записи ИННок.
2. Пустая таблица, в которую будут отправляться дубли по задействованным
   ИННкам. Схема = (no, inn, valid_from, valid_to, email_submitter_1,
   email_submitter_2, sub_date, report_date), где email_submitter_1/_2 –
   почта того, кто прислал ИННки первым/вторым, sub_date – дата повторной
   попытки поста ИННки в список.
3. Таблица с метриками, которые подвергаются влиянию проводимого пилота. На
   основании этой таблицы ИИ-агент сможет делать предложения запрашиваемой
   команде о том, может ли участие ИНН в прочих пилотах повлиять на метрику,
   измеряемую в потенциальном новом пилоте, и предлагать решения этого
   «перекрытия». Схема = (no, inn, pilot_name, valid_from, valid_to, measure,
   action, suggestion), где measure – метрика, на которую влияет участие
   ИННки в уже идущем пилоте, action – предлагаемое/предписываемое действие
   для заявителя ЦГ, suggestion – предложение по исправлению ситуации
   (замена/принятие риска/...).

### По шагам отработки агента:

1. На вход подается список ИННок. Агент проверяет файл на корректность
   заполнения: формат файла, отсутствие символов кроме чисел в записи ИНН.
   При некорректном заполнении агент пишет заказчику с просьбой переделать
   входной файл. При корректном заполнении — переход на следующий шаг.
2. Агент проверяет наличие ИННок из файла в источнике «задействованных
   ИННок», дописывает отсутствующие ИННки в источник. Главный критерий —
   отсутствие ИННок в файле в прошлых записях. Уточнение: при участии ИННок
   в качестве КГ они должны быть доступны как КГ для других пилотов — только
   потенциальное попадание в список ЦГ может повлиять на чистоту расчетов
   уже идущего пилота (**уточнить**). Если ИННка присутствует, агент
   проверяет дату valid_to как дату окончания пилота: если дата новой записи
   больше даты окончания пилота, запись не участвует в проверке и ИННка
   становится доступна для следующего пилота. При нахождении ИННок, уже
   участвующих в каком-либо пилоте, эти ИННки и номера строк отправляются
   команде разработки для оповещения. Пользователю направляется список
   повторяющихся ИННок с просьбой проверить список. Если список легитимен —
   запрашиваем сроки действия пилота и двигаемся на шаг 3.
3. Агент извещает заказчика о базовых проверках и пишет список свойств, по
   которым проводится разбиение списка ИНН на группы (сейчас: Отрасль по
   ОКВЭД, ОПФ, ТБ, Срок жизни в Сбере). Дополнительно можем предоставить
   (средний + суммарный) ЧОД, ЧЭП, Обороты, Выручка, СДО... Агент предлагает
   добавить в список имеющиеся проверки. Если нужной проверки нет, агент
   просит написать текст метрики — она высылается команде разработки для
   добавления. Если все поля выбраны — переход к шагу 4.
4. После выбора полей агент проводит расчеты и сохраняет 2 файла с КГ и ЦГ в
   отдельных файлах. Затем агент запрашивает внутреннюю почту пользователя
   (внутренний контур банка — поле ИНН переименовывается в `codes`, чтобы
   пересылка прошла) и отправляет файлы пользователю/иному получателю.
   Отдельно копия отправляется команде разработки.
5. Вместе с копией файлов агент высылает команде разработки данные по
   пилоту: срок проведения, частота расчетов (день/неделя/месяц), ФИО
   заказчика, статьи, по которым проводится оценка фин. эффектов. По
   названиям статей подбираются скрипты, рассчитывающие показатели фин.
   эффектов; результат сохраняется в папку пилота (Excel) для построения
   дэшборда в Навигаторе. Из файла с данными по пилоту агент забирает в
   Скилл параметр периодичности расчетов и автоматически пересчитывает
   скрипт с новыми данными, перезаписывая Excel (формат полной перезаписи
   или дописывания новых строк — **уточнить**).
6. После расчета и сохранения Excel файл подгружается в Навигатор как
   источник для дэшборда. После первой постройки дэшборда новые Excel файлы
   грузятся в том же формате, чтобы не порушить логику дэшборда.
7. Ссылка на дэшборд опционально направляется заказчикам пилота, в остальном
   используется командой аналитики.

---

Пункты, помеченные **(уточнить)** в оригинале, разрешены явными допущениями
в `README.md` этого пакета — см. раздел "Assumptions & open questions".
Ответы, полученные от автора ТЗ при постановке этой задачи:

- Атрибуты для группировки (ОКВЭД/ОПФ/ТБ/срок жизни, ЧОД/ЧЭП/Обороты/
  Выручка/СДО) считаются существующим "банком" PySpark-скриптов, по одному
  скрипту на метрику; агент триггерит нужный скрипт при выборе атрибута
  пользователем и переиспользует его же для последующего мониторинга пилота.
- Разбиение КГ/ЦГ: стратифицированный случайный сплит + проверка баланса по
  финансовым метрикам (с пересэмплированием при разбалансе).
- Интеграции (БД задействованных ИНН, отправка почты, загрузка в Навигатор)
  реализуются как заглушки/pluggable-коннекторы — в этой среде нет доступа к
  реальным системам Сбера, коннекторы рассчитаны на замену боевыми клиентами
  без изменения остального пайплайна.
