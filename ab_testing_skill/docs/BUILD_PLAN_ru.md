## 0. Главная мысль: сначала контракт, потом всё остальное

Два списка P1–P7 (из `chod_matching_review_ru.md` §5 и
`ab_split_calc_review_ru.md` §5) пересекаются, и шесть пунктов из них
упираются в одно и то же: **метрика возвращает одно число на клиента, а
нужна помесячная история**.

```
было:  run(...) -> {инн: 1234.5}
надо:  run(...) -> {инн: {'2026-01': 1234.5, '2026-02': ...}}
```

Без этого невозможны: окно однородности, траектория, когорты по динамике,
MDE (нужна дисперсия предпериода), `stat_significance`, и вся аналитика
пилота из раздела 4. С этим — каждый из них становится мелким.

Поэтому порядок работ не повторяет порядок приоритетов из разборов:
**Этап 1 делается первым и целиком**, иначе остальное придётся делать
дважды. Это единственный неразрывный кусок; всё, что после, можно
останавливать между пунктами.

## 3. Этап 3 — сам сплит и его измерение

Объединяет: `chod` M-P5 (направленное выравнивание), M-P6 (доминирующий
клиент), M-P1 (MDE), M-P4 (`stat_significance`).

### 3.1. Ререндомизация вместо 25 попыток

`split_homogeneity_review_ru.md` §4.1 и §6. Наш цикл уже является грубой
ререндомизацией, нужно три изменения в `skill/splitter.py`:

* число розыгрышей 25 → 1000+ (конфиг `max_reshuffle_attempts`);
* критерий — махаланобисово расстояние между средними по **всем**
  ковариатам, включая one-hot категориальных, вместо «худший SMD по
  финансовым статьям»;
* порог приёмки задаётся заранее; если не достигнут — говорить об этом
  явно, а не возвращать молча лучшую из попыток.

**Обязательно к сведению:** ререндомизация меняет референсное распределение,
поэтому финальный вывод об эффекте — рандомизационный, а не t-тест.
Учитывается в 3.4.

**Честный потолок:** при N=200 и 12 ковариатах порог 0,1 недостижим
(плато 0,22, проверено). На малых списках набор ковариат сокращать.

### 3.2. Доминирующий клиент

Аналог `MAX_PAIR_SHIFT`: если один клиент даёт больше X% суммы метрики
своей группы, никакое разбиение не сбалансируется. Считать на входе,
писать в `strata_warnings()` и в пакет аналитики.

### 3.3. MDE на входе — самое ценное для бизнеса

Сейчас `expected_effect_pct` собирается, валидируется и **нигде не
используется**. Считать до запуска по дисперсии предпериода:

```
MDE = (t_{1−α/2} + t_{power}) · SD/√n / base
```

и сравнивать с заявленным эффектом. Отказ или явное предупреждение:
«50 клиентов, разброс ЧОД такой-то ⇒ различимый эффект ≈ ±40%, заявлено 5%».

### 3.4. `stat_significance` — заполнить

Колонка-заглушка в `exporter.write_financial_effect_file`. Писать:
t-тест по разнице групп, **тест знаков**, и правило чтения из методологии
(«t значим, знаки нет ⇒ эффект держится на нескольких крупных»). Плюс
перестановочный тест со сменой знака (`chod_matching_review_ru.md` §3.5) —
он же закрывает оговорку из 3.1.

## 4. Этап 4 — НОВОЕ: финансовая аналитика пилота

То, что обсуждалось в этой сессии: после сплита группы надо вести во
времени и видеть, как пилот работает.

**Хорошая новость:** временной ряд уже копится. `financial_effect.xlsx`
пишется в режиме `append`, по блоку строк на каждый `report_date`, с
колонками `report_date, codes, group, <статьи>, stat_significance`. Аналитика
— это слой чтения поверх уже существующего файла, не новый сбор данных.

### 4.1. Ядро расчёта: `skill/analysis.py` (новый)

Одна функция `analyse_pilot(pilot_folder) -> PilotAnalysis`, читает
`financial_effect.*` + `pilot_meta.json` + `homogeneity_checks.csv`.

Что считает:

| Блок | Содержание |
|---|---|
| **Группы как целое** | по каждому `report_date`: среднее КГ, среднее ЦГ, разница, DiD к базовому периоду, накопленный эффект в рублях |
| **Статистика** | эффект с ДИ, p-value, тест знаков, MDE, доля пар/клиентов с положительной динамикой |
| **Индивидуальные тренды** | на клиента: наклон за период, вклад в эффект группы; топ-N драйверов и топ-N «тянущих вниз» в каждой группе |
| **Концентрация** | доля эффекта, приходящаяся на 1 / 5 / 10 крупнейших клиентов — прямое продолжение 3.2 |
| **Качество сравнения** | история `homogeneity_checks.csv`: с какого месяца группы разошлись |
| **Предупреждения** | недогруженный последний месяц, выбывшие клиенты, расхождение базы |

### 4.2. Три варианта подачи — выбрать завтра

Считает одно ядро, различаются только рендеры (как `skill/output.py`):

* **A. Excel-отчёт.** Лист «Динамика» + линейные графики средних по
  месяцам, лист «Клиенты» с трендами, лист «Выводы». Дешевле всего,
  ложится в текущую доставку письмом, аналитик открывает привычный файл.
  `openpyxl.chart.LineChart`; в форке есть готовый `line_chart` в
  `skill/xlsx.py`.
* **B. HTML-дашборд.** Статическая страница, перегенерируется на каждом
  пересчёте, без бэкенда — как остальные наши формы. Графики инлайновым
  SVG. Лучше всех смотрится и пересылается ссылкой.
* **C. Текстовый экономический обзор.** Детерминированный шаблон,
  заполняемый числами (не свободный текст): «ЦГ растёт на X% в месяц
  против Y% у КГ; накопленный эффект Z руб.; 47% эффекта даёт один клиент;
  с марта сопоставимость групп нарушена». Идёт в письмо и в
  `--output text`, и именно это читает агент.

**Рекомендация:** делать C + A сразу (они почти бесплатны поверх ядра),
B — отдельным шагом, если понравится.

### 4.3. Как запускается

Новая команда `python -m skill.cli report --pilot-folder <папка>`, и тот же
вызов автоматически в конце `run_recalculation`, чтобы отчёт обновлялся сам
на каждом пересчёте.

## 7. Этап 7 — тесты (в конце, как просили)

Отдельным проходом после Этапов 1–6:

* **Регрессия контракта:** плоский и помесячный ответ метрики дают
  одинаковый результат там, где это должно быть так.
* **Когорты:** клиент каждого типа траектории попадает в свою когорту;
  граничные случаи `F≤0`, `L≤0`, все нули.
* **Ререндомизация:** худший SMD монотонно не растёт с числом розыгрышей;
  порог соблюдается или об этом сказано; при N=200 честно сообщается, что
  порог недостижим.
* **MDE:** пилот из 50 клиентов с заявленным эффектом 5% отклоняется;
  из 5000 с 15% — проходит.
* **Аналитика:** на синтетическом пилоте с известным эффектом +15% ядро
  возвращает оценку в пределах ДИ; на A/A-пилоте (эффекта нет) — не
  рисует эффект. Это прямой аналог проверки из методологии, раздел 12.
* **Концентрация:** пилот, где один клиент даёт 47% эффекта, помечается.
* **Сверка:** строк на входе = в сплите + исключено с причиной.

Ориентир — довести с 163 до ~220 тестов.
